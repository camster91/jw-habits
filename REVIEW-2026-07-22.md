## P0 — Fix now

### P0-1 · Android keystore passwords leaked in git history

**Files:** `scripts/generate-android-keystore.sh` AND `android/app/build.gradle` (per Task 2 subagent). Originally committed in `cb976d5` (2026-03-02), redacted in `3dbb112` (2026-06-30).

**Evidence:**
```
git log --all -S "jwnews-2024-prefix" -- scripts/generate-android-keystore.sh
cb976d5 2026-03-02 Prepare for App Store submission: fix iOS config, add scripts and assets
3dbb112 2026-06-30 chore(jw-habits): remove stale docs + broken dev scripts
```

Two passwords were committed and are still in `git log`:
- `KEYSTORE_PASSWORD="[REDACTED]"` / `KEY_PASSWORD="[REDACTED]"` (full values in 1Password under `JW Habits / Android Signing (2026 rotation)`)
- `storePassword '[REDACTED]'` / `keyPassword '[REDACTED]'` in `android/app/build.gradle` (Task 2 found this — broader blast radius than the script alone)

**Impact:** Anyone with read access to the repo (today or via future mirror/backup leak) gets the **production Android keystore credentials** for `com.ashbi.jwnews`. Whoever has these can sign and publish malicious updates to the live Google Play listing that would be installed over the genuine app on every user's device.

**Fix:**
1. **Assume the keys are burned.** Generate a fresh keystore in Google Play Console (App signing → upload key reset). Coordinate with Google Play support to enroll the new key.
2. Rotate all secrets that share the prefix.
3. Purge from history (BFG or `git filter-repo`) — but only after #1, since once the keystore is rotated the historical values are inert.
4. Add `scripts/generate-android-keystore.sh` and `android/app/build.gradle` patterns to `.gitignore`'s hard-deny list. Use `git secret` or pre-commit hooks for any future secret commits. Add `gitleaks` to `ci.yml` so future secret leaks get caught at PR time.
5. Update CLAUDE.md with the "do not commit credentials" rule.

### P0-2 · Dockerfile nginx config diverges from `nginx.conf` (no gzip, no security headers in prod)

**Files:** `Dockerfile:15-23` (inline `RUN echo '...'`) vs `nginx.conf:1-53` (full config)

**Evidence:** The Dockerfile's inline `RUN echo 'server { listen 80; location / { try_files ... } location /assets/ { expires 1y; ... } }' > /etc/nginx/conf.d/default.conf` ships to prod. It has:
- ❌ No `gzip` directives
- ❌ No `X-Frame-Options`, `X-XSS-Protection`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` security headers
- ❌ No `Cache-Control: no-cache` for `/sw.js` (PWA update flow is broken)
- ❌ No MIME type for `/manifest.webmanifest`

The standalone `nginx.conf` has all of these. **Two configs, one ships, one is correct.**

**Impact:** Live at `https://jwhabits.ashbi.ca` is missing security headers (X-Frame-Options, etc.). PWA service-worker updates silently fail to apply because the SW is being cached. Manifest MIME type is wrong.

**Fix:** Replace the `RUN echo '...' > /etc/nginx/conf.d/default.conf` block with `COPY nginx.conf /etc/nginx/conf.d/default.conf`. Two lines, no risk.

### P0-3 · `deploy-coolify.yml` clobbers the real `Dockerfile` if it ever runs

**File:** `.github/workflows/deploy-coolify.yml:32-46`

**Evidence:** The workflow still triggers on `push: branches: [main]`. Inside the build job:
```yaml
- name: Build Docker image
  run: |
    cat > Dockerfile << 'EOF'
    FROM nginx:alpine
    COPY dist /usr/share/nginx/html
    COPY nginx.conf /etc/nginx/conf.d/default.conf
```

This **overwrites the real `Dockerfile` in the runner workspace** with a stripped-down throwaway version, then `scp-action` ships that throwaway Dockerfile (and a stripped `nginx.conf`) to the VPS. The Coolify path also runs `docker build` on the VPS using this throwaway Dockerfile.

**Impact:** If `deploy-coolify.yml` ever fires (still wired to `push: main` + `workflow_dispatch`), the production VPS deploys from the throwaway Dockerfile regardless of what `Dockerfile` looks like in `main`. Any future fix to `Dockerfile` (e.g. the P0-2 fix) is silently ignored.

**Fix:** Delete `.github/workflows/deploy-coolify.yml`. The actual deploy is `deploy-ashbi.yml` (Traefik + GHCR pull). Add a note in `deploy-ashbi.yml` that it supersedes the Coolify path.

### P0-4 · `streak.js` `todayProgress` truthy-checks a value that's now `{done, note}` — counting un-checked rows as done

**File:** `src/utils/streak.js` (referenced by `src/pages/Home.jsx:7`)

**Evidence:**
```js
// streak.js (current)
export function todayProgress(done, keys) {
  ...
  if (done[k]) count++;   // truthy on {done:false, note:'abc'} → false positive
}
```
The `done` shape per CLAUDE.md was `{ today: true, text: false, ... }`. Recent changes added per-row `note` support, so the value is now `{ done: false, note: 'abc' }`. Truthy-check counts the note-only row as done.

**Impact:** A user who taps "note" on a habit row but doesn't check it off gets counted as having done that habit. Streaks are inflated. `home.streakToday` count is wrong.

**Fix:** Change `if (done[k])` to `if (done[k]?.done ?? done[k])` (preserve legacy-bool compat) or use the helper `isDone(done[k])` if it exists. The same class of regression already needed a fixture patch in PR `d12e8e8` (`_verify` T4 line 222). Add a regression test in `streak.test.js` for the note-only case.

### P0-5 · `@capacitor/push-notifications` declared + configured, never registered

Grep confirms no `PushNotifications` import anywhere in `src/`.

**Fix:** Remove `@capacitor/push-notifications` from `dependencies`. Remove the `PushNotifications` block from `capacitor.config.json`. Strip the push entitlement from `ios/App/App/Info.plist`. Verify `ios-testflight.yml` still succeeds.
