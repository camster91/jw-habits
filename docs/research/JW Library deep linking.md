# Route Faithful Days links through jw.org/finder

Faithful Days can open content in JW Library without detecting anything or adding a plugin config, as long as it uses one URL shape. **Every link should be `https://www.jw.org/finder?...`, opened through the operating system and never through an in-app browser.** jw.org's association files claim exactly one path, `/finder`, for JW Library on both iOS (`3UJRAJWZ4R.org.jw.jwlibrary`) and Android (`org.jw.jwlibrary.mobile`). When JW Library isn't installed, the same URL falls back to the matching jw.org or wol.jw.org page in the default browser ([jw.org AASA](https://www.jw.org/.well-known/apple-app-site-association), [jw.org assetlinks.json](https://www.jw.org/.well-known/assetlinks.json)). **wol.jw.org publishes no association file, so the app's current wol.jw.org daily-text and meetings links will always open in a browser** ([Apple CDN for wol.jw.org: 404](https://app-site-association.cdn-apple.com/a/v1/wol.jw.org)). The daily text and Bible chapters are easy to fix, because both can be built from a date or a verse code. The weekly meeting articles are harder. Each needs a document id (`docid`) that can't be reliably computed, and jw.org's terms of use forbid shipping a tool that scrapes those ids at runtime. One caveat covers the whole report: none of this was tested on a physical device. The app hand-off rests on measured association files, Capacitor's source code and Apple/Android documentation. A device test is the first thing to do before shipping.

## Finder links carry one selector plus a language code

The finder is an undocumented redirect service. I found no official jw.org page describing its parameters, so everything below comes from live GET probes on 2026-10-07 and from community code. One trap in the probing: `curl -I` (HEAD) wrongly returned 404 for several valid links, so finder links must be tested with GET ([finder probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&pub=nwtsty&bible=19001001)). Each link needs one content selector, `docid`, `pub` (optionally with `issue` or `bible`), `bible` on its own, `alias` or `lank`, plus `wtlocale` for the language.

| Parameter | Meaning (measured unless noted) |
|---|---|
| `wtlocale` | Language code, case-insensitive: `E` gives /en/, `S` gives /es/, `F` gives /fr/. **If it's missing, the browser's Accept-Language decides the language**, so always include it. An unknown code goes to the home page. ([S probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=S&prefer=lang&docid=202026256), [no wtlocale](https://www.jw.org/finder?docid=2026520)) |
| `srcid` | A referrer tag. `jwlshare` (JW Library's Share button), `share` (the website) and no value all redirect identically ([probe](https://www.jw.org/finder?srcid=share&wtlocale=E&docid=2026520), [JWStreak](https://github.com/Hiburger/JWStreak/blob/main/lib/app_constants.dart)) |
| `prefer` | `lang`, `content` and no value all redirect identically on the web. It probably only matters inside the app, which is unconfirmed ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=SV&prefer=content&pub=nwtsty&bible=43003016)) |
| `alias` | `daily-text` works. `meetings` works without a date. Unknown aliases go to the home page ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&alias=foobar)) |
| `date` | Used with `daily-text`, written as `YYYYMMDD`. An invalid or unpublished date silently gives today's text ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&alias=daily-text&date=20301231)) |
| `pub` / `issue` | `nwtsty` (Study Bible), `nwt`, `es26`, `sjjm`. `pub=w&issue=202608` or `pub=mwb&issue=202609` go to an issue's table of contents ([mwb issue](https://www.jw.org/finder?wtlocale=E&pub=mwb&issue=202609)) |
| `docid` | A language-independent MEPS document id, 7 or 9 digits. An unknown id goes to the home page ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&docid=9999999999)) |
| `par` | Paragraph anchor: `docid=2026520&par=5` appends `#p5` ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&docid=2026520&par=5)) |
| `bible` | `BBCCCVVV` (book, chapter, verse). Ranges are written `BBCCCVVV-BBCCCVVV`. Verse `000` means the whole chapter. Defaults to `nwtsty` |

The `bible` code uses canonical book order (19 = Psalms, 43 = John). `bible=19023001-19023006` redirects to `/psalms/23/#v19023001-v19023006`. **`bible=19001000` opens the whole chapter**, which is the right form for a "read this chapter" button. A range that crosses chapters is clamped to the end of the first chapter ([Ps 23 range](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&pub=nwtsty&bible=19023001-19023006), [whole chapter](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&pub=nwtsty&bible=19001000), [cross-chapter](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&pub=nwtsty&bible=19023001-19024002)). Errors fail softly: a bad link returns a 302 to the language home page, never a 404. So a link generator can't check its own output from the status code alone.

The four example links all resolve correctly. **`alias=daily-text&date=20261007`** goes through a second finder on wol.jw.org to `wol.jw.org/en/wol/h/r1/lp-e/2026/10/7`, the daily-text page for 7 October 2026. That page shows a three-day window, 6–8 October ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&alias=daily-text&date=20261007)). **`pub=nwtsty`** goes to the Study Bible book index, not a particular verse ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&pub=nwtsty)). **`docid=2026520`** is the Watchtower study article "Resist Satan's Tactics—Trust In Jehovah and In Jesus" from the August 2026 study edition, studied the week of 5–11 October ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&docid=2026520)). **`docid=202026256`** is the Life and Ministry Meeting Workbook schedule for 5–11 October 2026 ([probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&docid=202026256)). The two docids return the same documents in Spanish and French, with localized slugs, when only `wtlocale` changes. So one stored docid serves all three languages ([F probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=F&prefer=lang&docid=2026520)).

## Only www.jw.org/finder hands off to JW Library

**On iOS**, jw.org's `apple-app-site-association` file lists JW Library (and a `-dev` build) for path `/finder` only. It excludes any URL ending in the fragment `#suppress_app_links`, and Apple's CDN serves identical copies for `www.jw.org` and `jw.org` ([Apple CDN www.jw.org](https://app-site-association.cdn-apple.com/a/v1/www.jw.org)). Apple documents that when no app handles a universal link, iOS sends it to the default browser ([Apple: canOpenURL](https://developer.apple.com/documentation/uikit/uiapplication/canopenurl(_:))). **On Android**, `assetlinks.json` verifies `org.jw.jwlibrary.mobile`, and Google's Digital Asset Links API returns the same statement ([Google DAL API](https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://www.jw.org&relation=delegate_permission/common.handle_all_urls)). A manifest dump of the December 2024 APK shows an https filter for host `www.jw.org` with `pathPrefix /finder`, alongside `jwlibrary:` and `jwlplaylist:` schemes ([TapTrap dataset](https://github.com/beerphilipp/taptrap/blob/main/vulnerable_app_detection/results/2025-05-20/output/org.jw.jwlibrary.mobile.json)). From Android 12, a web link goes to the default browser unless an app is verified for that domain, so there is no chooser dialog ([Android 12 behavior changes](https://developer.android.com/about/versions/12/behavior-changes-all#web-intent-resolution)). The TapTrap dump strips the `autoVerify` attribute, so I couldn't confirm it on the current APK. The JWStreak project says it checked the installed manifest and found `autoVerify=true` for `/finder` only, and that wol.jw.org is not registered ([JWStreak](https://github.com/Hiburger/JWStreak/blob/main/lib/app_constants.dart)).

The custom scheme is **`jwlibrary:///finder?` followed by the same query string** (three slashes, no host). It's registered on Android according to the manifest dump. On iOS the evidence is only community usage: Obsidian plugins build `jwlibrary:///finder?bible=…&wtlocale=…` and `jwlibrary:///finder?wtlocale=…&docid=…&par=…` ([obsidian-library-linker](https://github.com/msakowski/obsidian-library-linker/blob/main/src/utils/convertPublicationReference.ts), [Bible Linker Pro](https://github.com/Floydv149/bibleLinkerPro/blob/main/README.md)), and JWStreak ships the daily-text form and lists `jwlibrary` in its iOS `LSApplicationQueriesSchemes` ([JWStreak Info.plist](https://github.com/Hiburger/JWStreak/blob/main/ios/Runner/Info.plist)). `jwpub://` is not a registered URL scheme. Nobody documents the scheme officially, so it could change without notice. The scheme's one advantage is that it ignores a user who has turned off "Open supported links" for JW Library on Android, or who chose "Open in Safari" for jw.org on iOS (a choice iOS remembers).

## Capacitor's system paths keep the hand-off; @capacitor/browser kills it

The launch method matters as much as the URL. On iOS, Capacitor sends any navigation outside the app, and any `window.open(url, '_blank')`, to `UIApplication.shared.open(url, options: [:])` ([WebViewDelegationHandler.swift](https://github.com/ionic-team/capacitor/blob/main/ios/Capacitor/Capacitor/WebViewDelegationHandler.swift)), and `AppLauncher.openUrl` calls the same API ([AppLauncherPlugin.swift](https://github.com/ionic-team/capacitor-plugins/blob/main/app-launcher/ios/Sources/AppLauncherPlugin/AppLauncherPlugin.swift)). That system call honours universal links. **`@capacitor/browser` instead presents SFSafariViewController** ([Browser.swift](https://github.com/ionic-team/capacitor-plugins/blob/main/browser/ios/Sources/BrowserPlugin/Browser.swift)), and universal links don't fire inside it ([Apple Dev Forums](https://developer.apple.com/forums/thread/50340)). On Android, WebView navigation outside the app runs `new Intent(ACTION_VIEW, url)` ([Bridge.java](https://github.com/ionic-team/capacitor/blob/main/android/capacitor/src/main/java/com/getcapacitor/Bridge.java)), and `AppLauncher.openUrl` does the same ([AppLauncherPlugin.java](https://github.com/ionic-team/capacitor-plugins/blob/main/app-launcher/android/src/main/java/com/capacitorjs/plugins/applauncher/AppLauncherPlugin.java)). But `@capacitor/browser` builds its Custom Tab with a `CustomTabsSession`, which Chrome documents as forcing the Custom Tab "even if the corresponding native app is installed" ([Chrome Custom Tabs](https://developer.chrome.com/docs/android/custom-tabs/guide-get-started), [Browser.java](https://github.com/ionic-team/capacitor-plugins/blob/main/browser/android/src/main/java/com/capacitorjs/plugins/browser/Browser.java)). Android's `window.open` is less certain. Capacitor never enables multiple windows, so `_blank` most likely navigates the main WebView and then fires ACTION_VIEW. That comes from reading the source, not from a test. **`AppLauncher.openUrl` is the explicit, predictable choice on both platforms.** One configuration trap: **never add `www.jw.org` to `server.allowNavigation`**, because finder links would then load inside the WebView and never reach the OS.

Neither Capacitor path can tell you whether the link opened in JW Library or in the browser. Both pass `options: [:]` rather than `universalLinksOnly`, so `completed` is true either way. Apple also says `canOpenURL` can't detect whether an app is installed to handle a universal link ([Apple: canOpenURL](https://developer.apple.com/documentation/uikit/uiapplication/canopenurl(_:))). If Faithful Days wants an explicit "Open in JW Library" button with an "Install JW Library" fallback, it needs a probe, using `AppLauncher.canOpenUrl` with these narrow declarations. On iOS, add `jwlibrary` to `LSApplicationQueriesSchemes` in `Info.plist`. Capacitor documents that undeclared schemes always return false, and Apple caps the list at 50 entries (25 for apps linked on iOS 27 or later). On Android 11+, add `<queries>` with `<package android:name="org.jw.jwlibrary.mobile"/>` and a VIEW intent for scheme `jwlibrary` ([Capacitor App Launcher docs](https://capacitorjs.com/docs/apis/app-launcher)). These avoid the restricted `QUERY_ALL_PACKAGES` permission, and JWStreak is a shipped precedent for them ([JWStreak AndroidManifest](https://github.com/Hiburger/JWStreak/blob/main/android/app/src/main/AndroidManifest.xml)). Don't call `openUrl('jwlibrary:…')` without checking first. If JW Library is missing, the call just resolves `completed:false` and the user sees nothing.

## Daily text and Bible links are easy; meeting links need a docid

**Today's daily text** should use JW Library's own share format: `https://www.jw.org/finder?srcid=jwlshare&wtlocale={E|S|F}&prefer=lang&alias=daily-text&date=YYYYMMDD`. Build the date from the device's local calendar date, zero-padded and without dashes. The browser fallback lands on `wol.jw.org/{en|es|fr}/wol/h/{r1|r4|r30}/{lp-e|lp-s|lp-f}/YYYY/M/D`, with no zero padding in that path ([S probe](https://www.jw.org/finder?wtlocale=S&alias=daily-text&date=20261007)). Past and future dates work: 2020-01-01 and 2027-12-31 both resolved to dated pages, because the 2027 booklet is already online ([2027 probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=E&prefer=lang&alias=daily-text&date=20271231)). The notes disagree on the dashed form `date=2026-10-07`. One probe saw it pass through, another got a 404 ([dashed probe](https://www.jw.org/finder?wtlocale=E&alias=daily-text&date=2026-10-07)), possibly because of the HEAD/GET trap, so **use only `YYYYMMDD`**. **A Bible chapter** is `https://www.jw.org/finder?srcid=jwlshare&wtlocale={E|S|F}&prefer=lang&pub=nwtsty&bible=BBCCC000`. In Spanish this lands on, for example, `/es/biblioteca/biblia/biblia-estudio/libros/juan/3/` ([S Bible probe](https://www.jw.org/finder?srcid=jwlshare&wtlocale=S&prefer=lang&pub=nwtsty&bible=43003016)). Faithful Days already builds finder Bible links, so those links only need to go through a system launch path.

**Meetings are the hard case.** The midweek (mwb) and weekend Watchtower (WT) articles only open in JW Library through `docid` links, and the docids follow an almost-pattern that breaks in practice. The WT study ids roughly follow `YYYY·1000 + 200 + 40·issueMonth + k`, but they skip values (242, 563, 564, 603) and include an out-of-order 2026280. The mwb blocks step by 80 per issue until the September–October 2026 issue jumps to 252–259 instead of starting near 321 ([wol meetings 2026/41](https://wol.jw.org/en/wol/meetings/r1/lp-e/2026/41)). **A formula would produce wrong links, so docids have to be looked up.** The pub-media API returns `"docid":0` for every workbook week, so it can't be used for that ([GETPUBMEDIALINKS](https://b.jw-cdn.org/apis/pub-media/GETPUBMEDIALINKS?pub=mwb&issue=202609&langwritten=E&output=json&fileformat=RTF)). Three ways work without fetching anything. The first is `https://www.jw.org/finder?wtlocale=E&alias=meetings`, which resolves to the current week on wol, but returns 404 when a date is added ([probe](https://www.jw.org/finder?wtlocale=E&alias=meetings)). Because it's a `/finder` URL, the OS will offer it to JW Library, but **nobody has tested whether JW Library understands `alias=meetings` or opens its Meetings tab**. The second is the date-based wol URL `wol.jw.org/{lang}/wol/meetings/{r}/{lp}/{ISOYEAR}/{ISOWEEK}`, built from the ISO-8601 Monday-based week number. 2026 has a week 53, and Dec 29 2025 counts as 2026/1. The third is wol's own finder, `wol.jw.org/wol/finder?alias=meetings&wtlocale=E&date=YYYY-MM-DD` ([probe](https://wol.jw.org/wol/finder?alias=meetings&wtlocale=E&date=2026-10-19)). The second and third always stay in the browser. A no-meeting week, such as the 2026 Memorial week (ISO 14), still resolves but shows only a table of contents ([2026/14](https://wol.jw.org/en/wol/meetings/r1/lp-e/2026/14)).

## The terms allow links but rule out shipping a docid scraper

jw.org's Terms of Use prohibit creating, "for distribution purposes, any software applications, tools, or techniques that are specifically made to collect, copy, download, extract, harvest, or scrape data, HTML, images, or text from this site" ([jw.org Terms of Use](https://www.jw.org/en/terms-of-use/)). Fetching wol meetings pages at runtime to read the two `/wol/d/` docids would work technically. Each week's page contains exactly the mwb and WT ids ([2026/42](https://wol.jw.org/en/wol/meetings/r1/lp-e/2026/42)). But it is exactly the kind of distributed extraction tool that clause targets. The same terms also forbid sharing "links to or electronic copies of downloadable publications". My reading, which is not legal advice, is that this clause aims at redistributing download files, not at linking to articles. jw.org's own share buttons generate `finder?srcid=jwlshare` links, and JW Library emits them too. So plain finder links are the expected use. A hand-maintained docid table bundled with the app avoids runtime scraping. Building it still means harvesting docids from wol, so it remains a grey area. The safest docid source is one the user pastes from JW Library's Share sheet.

## Recommendation for Faithful Days

Change the daily-text button from its wol.jw.org URL to the `alias=daily-text` finder link, and open every finder link with `AppLauncher.openUrl`. Keep `@capacitor/browser` only for an explicit "Open on the web" option. Map the app language to `wtlocale` (`en` to `E`, `es` to `S`, `fr` to `F`) and always include it. For meetings, keep the date-based wol meetings URL as the dependable web link. Add an optional "Open in JW Library" action that sends `https://www.jw.org/finder?wtlocale=X&alias=meetings`, but only after a device test confirms the app handles it. Otherwise that button would just repeat the wol page. If JW Library-first behaviour has to be guaranteed, add the `jwlibrary` declarations and branch on the probe:

```ts
import { AppLauncher } from '@capacitor/app-launcher';
const LOCALE = { en: 'E', es: 'S', fr: 'F' } as const;

function finderQuery(lang: keyof typeof LOCALE, sel: Record<string, string>) {
  return new URLSearchParams({ srcid: 'jwlshare', wtlocale: LOCALE[lang], prefer: 'lang', ...sel }).toString();
}
const ymd = (d: Date) =>
  `${d.getFullYear()}${String(d.getMonth() + 1).padStart(2, '0')}${String(d.getDate()).padStart(2, '0')}`;

export const dailyText = (lang, d = new Date()) => finderQuery(lang, { alias: 'daily-text', date: ymd(d) });
export const bibleChapter = (lang, book: number, ch: number) =>
  finderQuery(lang, { pub: 'nwtsty', bible: `${String(book).padStart(2, '0')}${String(ch).padStart(3, '0')}000` });

export async function openInJwLibrary(qs: string, preferScheme = false) {
  if (preferScheme && (await AppLauncher.canOpenUrl({ url: 'jwlibrary://' })).value) {
    return AppLauncher.openUrl({ url: `jwlibrary:///finder?${qs}` });
  }
  return AppLauncher.openUrl({ url: `https://www.jw.org/finder?${qs}` }); // app if installed, else browser
}
```

The device test should cover four things on iOS and Android, each with and without JW Library installed. First, a finder link opened by `AppLauncher.openUrl` lands in JW Library. Second, `window.open(..., '_blank')` behaves the same on Android. Third, JW Library honours `date`, `par`, verse ranges and `alias=meetings`. Fourth, the `jwlibrary:` scheme is registered on iOS.

## Conclusion

The real constraint is the host, not the parameters. Moving from `wol.jw.org` to `www.jw.org/finder` is the change that decides whether JW Library opens, and Faithful Days can make it for the daily text and Bible today, with no new permissions. Meetings are a content problem rather than a linking problem. JW Library is keyed by docid, the docid sequence is irregular, and the terms forbid the obvious automated lookup, so for now the weekly material stays a web link unless a device test shows `alias=meetings` opening inside the app. Because the finder fails softly, add a lightweight developer-side check that compares the final URL against the language home page. Otherwise a broken link would ship unnoticed.
